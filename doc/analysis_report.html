1. 项目概述

这是一套面向 AI 加速芯片（a6 架构）的硬件任务调度器。它把一个静态的算子依赖图（DAG，共 864 个任务）调度到分层硬件拓扑上执行，利用硬件队列（GQM/MSGQ 寄存器）与硬件计数器（publish/subscribe + SCB）完成任务的入队、取队与依赖同步。

  • 负载分发：把任务推送到离执行核最近的队列，队列满时逐级上浮（cluster → die → chip）。
  • 数据局部性：后继任务被放到「前驱任务」所在的 cluster，减少跨簇搬数。
  • 依赖驱动 + 提前派发：任务在其依赖基本满足（还剩 ≤1 个前驱）时就提前入队，靠硬件计数器在真正执行前做最后一道同步。

3. 硬件拓扑与三级队列

3.1 硬件拓扑（自底向上）

CHIP (1)  →  DIE (2)  →  CLUSTER (每 die 6 个)  →  AICORE (每 cluster 10 个)
                        TOTAL: 1 芯片 / 2 die / 12 cluster / 120 AI core
常量值含义
CLUSTER_PER_DIE6每个 die 内的 cluster 数
AICORE_PER_CLUSTER10每个 cluster 内的 AI core 数
CUBE_PER_AICORE / VECTOR_PER_AICORE1 / 1每 core 含 1 个 Cube + 1 个 Vector 单元
CORE_PER_DIE6×10 = 60每个 die 的 core 数
TOTAL_CORE_NUM2×60 = 120全芯片 core 数

core 编号是连续的（0..119），由 core_id_to_die / core_id_to_cluster 反解出所属 die 与 cluster。

3.2 三级队列 × 三种任务类型

队列自底向上镜像硬件拓扑，共三级；每级又按任务类型拆成独立队列：

级别单位数× 3 类型队列总数
Cluster 队列12CUBE / VECTOR / MIX36
Die 队列2CUBE / VECTOR / MIX6
Chip 队列1CUBE / VECTOR / MIX3
合计——45

队列描述符 task_queue_desc_t 只有 base（硬件寄存器基地址）与 size 两个字段。基地址按「层级偏移 + 类型偏移」连续排布（当前都是 0x1 的占位偏移，见 TCM_* 宏）。

3.3 坐标编码

// 打包：高字节 = die_id，低字节 = cluster_id
TASK_COORD(die, cluster) = (die << 8) | cluster
TASK_COORD_INVALID = 0xFF   // 任务被上浮到 die/chip 队列后，该位置未知

4. 任务类型

枚举值含义
CUBE0矩阵/卷积类算子，由 Cube 单元执行
VECTOR1向量类算子，由 Vector 单元执行
MIX2混合算子（可被两类单元处理）

数据集中 task_type[] 取值覆盖 0/1/2 三种。每个 core 通过 run(bool isCube) 决定自己是 CUBE 还是 VECTOR 型执行单元，并按对应类型去 queue_pop。

5. 依赖图数据结构

所有数据都在 cases2/qwen3_14b_decode.h 中，以 static 数组形式给出，规模均为 total_task_cnt = 864：

数组类型含义

task_type[864]char任务类型 0/1/2（CUBE/VECTOR/MIX）
task_duration[864]int任务执行时长（周期数）
pre_idx[864]int该任务在 predecessors[] 中的起始下标
predecessors[]int扁平化前驱边列表

邻接表采用经典的「索引数组 + 扁平边列表」压缩表示：pre_idx[]/task_suc_idx[] 给出起始偏移，配合前驱/后继边列表进行遍历。

6. 运行总流程

整体是一个「生产者-消费者 + 依赖传播」的闭环，没有中央调度器，而是每颗 core 自主取任务、自主传播依赖：

┌─────────────────────────────── 派发端（生产者） ───────────────────────────────┐ │ 前驱任务完成 → on_task_done → resolve_dep │ │ · task_pre_cnt[succ]-- │ │ · 当 task_pre_cnt[succ] < EARLY_DISPATCH(2) 时 │ │ → queue_push_to_pre_coord( 前驱坐标, type, succ ) // 把后继推到前驱附近 │ └───────────────────────────────────────────────────────────────────────────────┘ │ 入队（硬件队列） ▼ ┌─────────────────────────────── 执行端（消费者） ───────────────────────────────┐ │ run(bool isCube)：每颗 core 死循环 │ │ · slot 空闲 → queue_pop 取一个任务 │ │ · slot 占用 → check_ostd_*：订阅前驱计数器 → 轮询 SCB 就绪条件 │ │ · 条件满足 → fake_kernel() 执行 → on_task_done → 回到派发端 │ └───────────────────────────────────────────────────────────────────────────────┘

两条数据流闭环：

  • 任务流：queue_push* 写队列 → queue_pop 读队列 → 执行。
  • 依赖流：完成后 publish（通知计数器）→ 后继 subscribe（订阅计数器）→ SCB 触发执行。

7. 关键函数详解

7.1 queue_init()

自底向上为 45 个队列计算并写入硬件寄存器基地址：

void queue_init(void)
{
    // level 0: 12 个 cluster × 3 类型
    for die ... for cluster ... for t in [0,3):
        g_cluster_queue[die*6 + cluster][t].base = cluster_queue_base(die, cluster, t);

    // level 1: 2 个 die × 3 类型
    g_die_queue[die][t].base = die_queue_base(die, t);

    // level 2: 1 个 chip × 3 类型
    g_chip_queue[t].base = chip_queue_base(t);
}

7.2 queue_push(core_id, type, task)

按 core_id 反解出 die/cluster，把任务推到「最近 cluster 队列 → 本 die 队列 → chip 队列」，哪级成功就在 task_coord[task_id] 记录对应坐标（未知位置用 0xFF）。

bool queue_push(uint32_t core_id, task_type_t type, uint64_t task)
{
    die_id = core_id_to_die(core_id);   cluster_id = core_id_to_cluster(core_id);
    cluster_q = die_id * CLUSTER_PER_DIE + cluster_id;

    if (gqm_push(g_cluster_queue[cluster_q][type].base, task))   // 最近 cluster
        { task_coord[task_id]=TASK_COORD(die, cluster); return true; }
    if (gqm_push(g_die_queue[die_id][type].base, task))       // 上浮 die
        { task_coord[task_id]=TASK_COORD(die, INVALID); return true; }
    if (gqm_push(g_chip_queue[type].base, task))             // 上浮 chip
        { task_coord[task_id]=TASK_COORD(INVALID, INVALID); return true; }
    return false;   // 全满
}

7.3 queue_pop(core_id, type, *task)

与 push 对称，先在本 cluster 队列取，再依次上浮；取出后同样更新该任务的 task_coord。

7.4 queue_push_to_pre_coord(coord, type, task)

与前两者不同，它不依赖 core_id，而是以前驱的打包坐标为锚点，把后继任务放到前驱所在 cluster（数据局部性最优），失败则上浮 die / chip：

bool queue_push_to_pre_coord(int coord, task_type_t type, uint64_t task)
{
    die_id = (uint8_t)(coord >> 8);   // 高字节
    cluster_id = (uint8_t)(coord & 0xFF); // 低字节

    // 前驱 die/cluster 有效时才尝试最近的 cluster 队列（防止 0xFF 越界）
    if (die_id < DIE_NUM && cluster_id < CLUSTER_PER_DIE)
        if (gqm_push(g_cluster_queue[die_id*6+cluster_id][type].base, task))
            { task_coord[task_id]=TASK_COORD(die, cluster); return true; }
    if (die_id < DIE_NUM)
        if (gqm_push(g_die_queue[die_id][type].base, task))
            { task_coord[task_id]=TASK_COORD(die, INVALID); return true; }
    if (gqm_push(g_chip_queue[type].base, task))
        { task_coord[task_id]=TASK_COORD(INVALID, INVALID); return true; }
    return false;
}

7.5 run(bool isCube)

每颗 core 的执行主循环，采用「双 slot（TASK_OSTD=2）」软流水，让一个任务的执行与另一个任务的依赖等待重叠：

void run(bool isCube) {
    core_id = get_coreid();
    type = isCube ? CUBE : VECTOR;

    while (true) {
        if (slot_free[0]) {                    // slot 0 空闲 → 取新任务
            task_id = INVALID_TASK_ID;
            queue_pop(core_id, type, &task_id);
            set_ipc_reg_0(task_id);           // 写任务上下文到 IPC 寄存器
            slot_free[0] = false;
        } else check_ostd_0();                 // slot 0 占用 → 轮询依赖/执行

        if (slot_free[1]) {                    // slot 1 同理
            task_id = INVALID_TASK_ID;
            queue_pop(core_id, type, &task_id);
            set_ipc_reg_4(task_id);
            slot_free[1] = false;
        } else check_ostd_1();
    }
}

7.6 check_ostd_0() / check_ostd_1()

当 slot 已被占用时，检查该 slot 上任务的依赖是否就绪：读任务 ID → 若还有前驱则 subscribe（订阅前驱完成计数器）→ 读 SCB 条件 → 条件满足则执行：

void check_ostd_0() {
    task_id = get_ipc_reg_0();
    if (task_id != INVALID_TASK_ID) {
        predecessor_id = get_ipc_reg_1();
        if (predecessor_id > 0) { subscribe(predecessor_id, 1, 0); } // 订阅前驱计数器==1
        cond = get_ipc_scb_0();              // 轮询同步计数器块
        if (cond > 0) {
            fake_kernel();                   // 依赖已满足 → 真正执行
            slot_free[0] = true;
            on_task_done(task_id);           // 完成后发布 + 传播
        }
    }
}

slot 0 使用寄存器 reg_0/reg_1/reg_2 与 scb_0，slot 1 使用 reg_4/reg_5/reg_6 与 scb_6，二者结构完全对称。

7.7 on_task_done() 与 resolve_dep()

任务完成的收尾：先发布计数器（publish，通知订阅方），再遍历所有后继，递减其依赖计数并在「依赖基本满足」时提前派发：

void on_task_done(task_id) { publish(task_id); resolve_dep(task_id); }

void resolve_dep(task_id) {
    succ_cnt = task_suc_cnt[task_id];
    if (succ_cnt <= 0) return;
    for k in [task_suc_idx[task_id], ...+succ_cnt):
        succ_id = task_successors[k];
        task_pre_xor[succ_id] ^= task_id;          // 记录已完成的前驱（异或）
        task_pre_cnt[succ_id]--;                   // 剩余依赖 -1
        if (task_pre_cnt[succ_id] < EARLY_DISPATCH) {   // < 2，即还剩 ≤1 个前驱
            type = task_type[succ_id];
            queue_push_to_pre_coord(task_coord[task_pre_xor[succ_id]], type, succ_id);
        }
}

EARLY_DISPATCH = 2 的含义：当后继还剩 1 个前驱未完成时就提前入队，把「取数/搬数」与最后那个前驱的执行重叠；真正执行前再由 subscribe 挂在那个前驱的计数器上做最后同步。

8. 任务生命周期时序

任务 T 的生命周期： [1] 派发 前驱完成 → resolve_dep 递减 task_pre_cnt[T] 当 pre_cnt < 2 → queue_push_to_pre_coord(前驱坐标, type, T) │ 写入硬件队列（cluster/die/chip） [2] 入队 task_coord[T] = 打包坐标 (die,cluster) [3] 取队 core 的 slot 空闲 → queue_pop(core, type, &T) → 写 IPC 寄存器 [4] 等待 读前驱 → subscribe(前驱计数器) → 轮询 get_ipc_scb_* [5] 执行 条件 cond>0 → fake_kernel()（当前为 TODO 桩） [6] 完成 on_task_done(T) → publish(T) + resolve_dep(T) → 回到 [1] 派发其后继

其中 [4]→[5] 是硬件计数器驱动的「最后一道依赖同步」，而 [1] 的提前派发是纯软件（队列）层面的。

9. 观察与潜在问题

以下为静态阅读代码时发现的、可能影响正确性/可读性的点（按重要程度排序）：

① 关键桩函数未实现。publish()、subscribe()、fake_kernel() 均为空实现（TODO），且 get_ipc_reg_* / set_ipc_reg_* / get_coreid() 等硬件原语当前只是返回常量（0..7）的占位宏。因此整条「计数器同步 + 真正执行」链路目前是逻辑骨架，尚未接通真实硬件。
② task_coord 为 static，跨编译单元存在多份副本。该数组定义在 cases2/qwen3_14b_decode.h 中且为 static，同时被 hw_queue.c（写入坐标）与 auto_kernel.c（读取前驱坐标）各自包含，于是二者访问的是各自独立的副本：写入不会反映到另一边的读取上，task_coord[task_pre_xor[succ]] 读到的将是全 0。要打通局部性调度，需把该数组改为非 static 的全局共享定义（或通过 extern 声明唯一实例）。
③ total_task_coord 是悬空声明。hw_queue.h 仍声明 extern int total_task_coord[]，但三个目录内既无定义、hw_queue.c 也已改用 task_coord，属于遗留声明，链接时会缺符号（若被引用）。
④ MIX 类型任务无人消费。run(bool isCube) 只把执行单元映射为 CUBE 或 VECTOR，queue_pop 也只会按这两种类型取队；而 task_type[] 中存在取值 2（MIX），这些任务会被 queue_push_to_pre_coord 推入 MIX 队列却永远不会被取出。
⑤ IPC 寄存器读写不完全对应。在 run() 中，slot 0 的 predecessor_id 未初始化即写入 reg_2；而 check_ostd_0() 却把 reg_1 当作 predecessor_id、把 reg_2 当作 context。二者对寄存器的分工不一致（slot 1 的 reg_5/reg_6 同理），疑似尚未定稿的寄存器接线。
⑥ task_pre_xor 非原子 + 初值可疑。task_pre_xor[succ] ^= task_id 是普通 int 的读-改-写，多颗 core 并发完成同一后继的前驱时会存在竞态；且从当前数据看，task_pre_xor 的初值与 pre_idx 完全一致，疑似生成脚本未正确初始化（期望值通常是「所有前驱 ID 的异或」或 0）。
⑦ gqm_push / gqm_pop 未定义。它们是硬件队列原语，仅在头文件中声明（本目录内无实现），依赖真实硬件/驱动环境提供；当前 TCM_* 基地址偏移也都是 0x1 占位值。

10. 结论

这套代码已经清晰地勾勒出一个无中央调度器、硬件队列 + 计数器驱动的任务调度骨架：

  • 分层队列（cluster/die/chip）× 三种类型（CUBE/VECTOR/MIX）实现了带「上浮」的负载分发。
  • queue_push_to_pre_coord 实现了「后继跟随前驱」的数据局部性调度。
  • resolve_dep + EARLY_DISPATCH=2 实现了提前派发，配合 subscribe/publish 做最终依赖同步。
  • 双 slot 软流水让取队、等待、执行互相重叠，隐藏依赖等待延迟。

主要风险集中在「桩函数未实现」与「跨编译单元的共享状态（task_coord/task_pre_xor）语义不正确」两处；在接通真实硬件之前，建议先修正 ②③④⑥ 中的数据一致性问题，使逻辑闭环成立。
